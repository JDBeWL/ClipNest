# 注释规范

适用于 `src/`、`tests/` 下的 C# 与 XAML，以及仓库根目录的 `.csproj`、`.props`。
生成代码、`obj/`、第三方源码不在范围内。
界面文案、异常消息、日志与断言消息也按本文写，它们分别是给用户、维护者与失败现场读的注释。

## 该写的四类

1. **约束**：为什么必须这样，不能那样。顺序、时机、前置条件。
   > 缩略图先写 `.tmp` 再改名，读取方要么看不到文件，要么看到完整文件。

2. **失败模式**：不这样会怎样。这是最有价值的一类，把踩过的坑变成一次性的。
   > 解码、编码与落盘不能回到 UI 线程的同步上下文，否则首次浏览时每张图都会在主线程上卡一下。

3. **契约**：谁调、什么时候调、谁不许调。
   > 暂停后不再领取新任务；正在处理的一张会完成，恢复时由调用方唤醒。

4. **不变量**：这里恒成立、别处可以依赖的事实。
   > 节点之间至少隔一张缩略图的空隙，放大后可以直接逐张点选。

## 不该写的四类

1. **改动叙事**：「原来是 X，现在改成 Y」「第一版」「后来换掉了」。
   时间轴对读者没有信息量，删掉时间轴只留结论，语义不减。
   > ✗ 现在缩略图按固定档位缓存
   > ✓ 缓存按长边分档；每档在磁盘与内存各留一份，因此只取固定档位，缩放条每动一格不会生成新文件。

   例外是迁移脚本。`Migration009` 需要说明它修的是哪一批旧数据，
   「早期按 EXIF 原始像素记录尺寸」是那条 SQL 的语义，不是叙事。

2. **调试现场**：「实测」「截图里」「调试时发现」。数据本身可以留，现场痕迹不要留。
   > ✗ 实测这台机器上 GPU 比 CPU 快三倍
   > ✓ DirectML 覆盖 Windows 上的 AMD、NVIDIA 与 Intel 显卡，失败时回退 CPU。

3. **测试自辩**：「为了单测」「否则测试过不了」「便于测试」。测试的困难不是设计的理由。
   > ✗ 抽成接口是为了单测能替换解码器
   > ✓ 解码器按扩展名选择，新增格式不必改调用方。

4. **复述代码**：把 `foreach` 翻译成中文。代码能读出来的，注释一个字都别重复。
   > ✗ 遍历解码器，找第一个能处理该扩展名的实现
   > ✓ 扩展名决定解码器。RAW 交给 LibRaw，HEIC 交给系统解码器，其余交给 Skia。

## 自检两条

- **删掉试试**：这条注释删了，会不会有人踩坑？不会就别写。
- **读给新人**：一个没见过旧版本的人读完，知不知道「这里为什么长这样」？

## 语域：书面，不拟人

注释是技术文档，不是对同事解释。判据只有一条，**读起来像规格说明，还是像口头讲解？**
后者读着亲切实则含糊。比喻能建立直觉，但说不清边界，而边界才是指注释的用处。

四条禁令：

1. **不拟人**：模块、解码器、队列、线程不「想」不「挡」不「吐」不「自己」做事。
   > ✗ 解码器自己会挡掉坏文件
   > ✓ 解码器在文件头无法解析时返回空值。

2. **不用口头量词与口头副词**：一把、干脆、才真的、就是、其实、差不多。
   > ✗ 导入时干脆把整批写进一个事务
   > ✓ 整批写入单个事务，中途失败不会留下半批资产。

3. **数据流用术语，不用吃喝动词**：灌、塞、喂、吐 → 写入、推送、供给、产出。
   > ✗ 导入完成后把整个图库灌给标注队列
   > ✓ 导入完成后向标注队列发一次信号，由队列从数据库领取待标注资产。

4. **口号式短句改完整条件句**：主语 + 条件 + 结论。破折号插入语拆成独立从句。
   > ✗ 看不懂的就不猜，交给调用方保留原样
   > ✓ 证据不足时不作判定，由调用方保留原值。

对照表（常见口语按下面这样换）：

| 口语 | 书面 |
| --- | --- |
| 挡一道 | 自行拦截 |
| 刷屏 | 日志洪泛 |
| 踩到 | 落于、触及 |
| 来回撞 | 反复重试 |
| 看不出 | 无法判定 |
| 就得 | 必须 |
| 别再 | 不得 |
| 收工 | 结束 |
| 顶在（UI 线程上） | 占用 |
| 引擎自己、线程自己 | 引擎自身、线程本身 |

第一类例外是领域术语。「拖拽」是 UI 动作，「主文件」指
`asset_files.is_primary` 的那一行，「瓦片」是虚拟化画布上的绘制单元，都不是口语。
把术语改成大白话反而降精度。

第二类例外是本来就在书面语里的说法。「宁可先留空位，也不让瓦片重叠」是规范汉语，
不算口语，改成「优先留空位而非重叠」反而更绕。判据是这句子放进说明书里违不违和。

异常消息与日志同样按书面语写，并给出下一步。

> `无法打开数据库：{path}。请确认目录可写，或设置 CLIPNEST_HOME 指向可写目录。`

一句话说清发生了什么、读者能做什么。只写「数据库打开失败」等于把问题退回给用户。

## 别解释代码结构

判据和「复述代码」那条一样。**删掉它，读代码的人会不会漏掉一个约束？** 不会就删。

一、**复述步骤**。步骤按定义就写在代码里，注释要写的是顺序为什么不能反、反了会怎样。

> ✗ 建库时依次执行 001 到 011 的迁移
> ✓ 每个迁移单独提交并立即写入 `user_version`；中途崩溃后下次启动从断点继续，已完成的迁移不会重放。

二、**翻译标识符**。`GetOrCreateAsync` 上面写「获取或创建缩略图。」是零信息，
摘要行要写成契约（输入范围、失败条件），不要写成同义反复。

> ✗ 获取或创建缩略图。
> ✓ 缓存命中直接返回路径；未命中时解码并写入缓存，解码失败返回 `null`。

三、**给局部变量作注**。有收益的可以留，例如「`known` 字典把每个文件的查找从线性扫描压到常数时间」；
只描述存了什么就删，例如「这里是已扫描文件的集合」。

四、**挂错位置**，最坏的一种。搬动代码时注释没跟着走，读者会以为它在讲当前这个函数。
例如把 `ThumbnailSizing` 的换算说明留在调用它的控件上，两条无关的话挤在一个块里，
看代码的人先被误导，再发现前后半截说的不是一件事。

这类问题编译器查不出来。开启 XML 文档生成后，它只报 `<see cref="Name"/>` 断链（CS1574），
报不出「挂错但解析成功」。能查的只有搬代码时那一眼。拖走一个函数，
顺手看一眼它头上的 `///` 还对不对。

## 括号

括号是注释里的省略号。写的人省了组织句子的力气，读的人多一次跳读。
能用分句说完的，就不要塞进括号。

保留三类：

1. **枚举与举例**：`格式角标（jpg、png、heic）的底色`。列表在括号里比在句子里好读。
2. **数值、单位、区间**：`缩略图长边（1024 px）`、`年份区间（2020..2024）`。
3. **标准与出处**：`对比度 ≥ 4.5:1（WCAG AA）`。

其余一律改成句子成分：

- 补充说明 → 逗号分句
  > ✗ 导入完成后刷新图库（只刷新一次）
  > ✓ 导入完成后刷新图库；每次导入只刷新一次。
- 同义解释 → 「，即……」
  > ✗ 列表主标题（文件名）
  > ✓ 列表主标题，即文件名。
- 跨引用 → 「，见 ……」
  > ✗ 选中态会额外加粗（见 `ThumbnailGridCanvas`）
  > ✓ 选中态额外加粗，见 `ThumbnailGridCanvas`。
- 返回值元组 → 直接陈述
  > ✗ 编译搜索结果 →（SQL, 参数）
  > ✓ 编译查询，返回 SQL 与绑定参数。

同一句里不要出现两对括号。两对就是两层插入语，句子已经散了，该重写。

## 形式

- 单个注释块 **≤ 3 行**。超了先怀疑自己是在解释代码结构，而不是在解释约束。
  `<remarks>` 单独计算，记录推导时可以到 6 行，再长就该挪进文档。
- 单行 **≤ 80 字**，理想是 50 上下。中文长句没有空格可断，超过两行宽度读者会滑行。
  命令行、`dotnet test …` 这类要完整复制的不拆。
- 两条上限会打架，压行宽就要多占行。冲突时**先守行宽**，
  块多一行比一行八十个字好读。
- 注释是散文，不用 markdown 列表、标题、表格、加粗。
  `<summary>` 与 `<remarks>` 是结构，不是排版。
  C# 的 XML 注释不渲染 markdown，`**` 与反引号只会原样出现在悬停提示里。
- 需要强调时调整语序或单独成句，不用 `<b>`、`<i>`。注释不是排版稿。
- `///` 写契约与理由，`//` 只写这一行非显然的意图。
- 文件级说明挂在命名空间下第一个类型上。C# 没有 `//!`，也不要写 `// File: xxx.cs` 这类零信息头。
- 悬停提示以 `<summary>` 为主，`<remarks>` 通常不展开。第一句要能独立回答
  「这是什么、什么时候用」，推导与失败模式放 `<remarks>`。
- 引用其它标识符用 `<see cref="Name"/>`，参数用 `<paramref name="x"/>`，
  行内代码用 `<c>…</c>`，不要用反引号。悬停里能点开的链接，比纯文本名字有用。
  本文为了排版用反引号标记代码，照抄进 `.cs` 时换成 `<c>…</c>`。
- `<param>` 只写名字看不出的约束，例如单位、范围、所有权；不要写「要处理的图片」。
  `ThumbnailSizing.ForBox` 的参数说明是范例，未知时怎么估算、缩放比指什么、超限怎么截断都写了。
  > `<param name="sourceRatio">图片宽高比；未知时按显示框较长的一边估算。</param>`
- `<returns>` 写空值与失败语义，不要写「返回结果」。
- `<exception>` 写触发条件，不要写「可能抛出异常」。
- 实现接口时用 `<inheritdoc/>`，不复制摘要。接口的契约只在接口上写一份。
- `<!-- -->` 只出现在 `.axaml` 与 `.csproj`、`.props` 里，写法与 `///` 相同。
  `Directory.Build.props` 里钉死 x64 的那段注释是范例，它说明的是约束，不是操作。

## 标点

四个高频误用，改起来最快，对观感的提升也最明显。

一、**破折号不当连接词**。它几乎只做一件事，即前半句说完、后半句补充。
按前后关系换成标点：

| 关系 | 改法 |
| --- | --- |
| 分句继续（后半句续前半句的谓语，或是它的同位语） | `，` |
| 因果、推论 | `，因为…` / `；否则…` / `。` |
| 并列、推进 | `。` |
| 转折 | `；但…` / `。` |

不列「换成 `：`」这一项。句中冒号已经全库禁用，见下文第四条。两套规则不能
互相拆台，破折号要换就直接落到句号、分号或逗号上。

> ✗ 创建会话。`allowGpu` 为假时固定走 CPU —— CLIP 的输入是动态形状，放 GPU 上会反复重编译
> ✓ 创建会话。`allowGpu` 为假时固定走 CPU；CLIP 的输入是动态形状，放 GPU 上会反复重编译。

破折号只留给真正的插入语，也就是删掉它、句子就不成立的地方。这样的地方很少。

判断要点是换完读一遍。**「。」之下前后各自独立，「，」之下后半句还得依附前半句。**
拿不准时用句号，多数情况下比逗号更清楚。

断言与界面字符串同样适用。断言消息的结构和注释一样，都是「现象 + 为什么要紧」。
读的人只在测试失败的那一刻看到它，因此更要把因果写明：

> ✗ `"分类数应该等于根标签数 —— 未分类也单独成簇"`
> ✓ `"分类数应该等于根标签数，因为未分类也单独成簇"`

界面文案也一样，用户读的是句子不是短语。改字符串时**不要碰占位符与绑定**，
`$"语义索引 {stats.Ready}/{total}"` 里的 `{stats.Ready}` 与 `{total}` 替换前后要逐个对得上，
XAML 里的 `{DynamicResource Brush.Text.Primary}` 同理。

二、**斜杠只用在代码与路径里**。`亮边 / 暗边` 读起来像文件路径。
中文并列用 `、` 或 `与`，两者不要混用。

替换时注意两种情形。三项以上用 `、`，两项用 `与`。原本表「或」的
（`打开 / 关闭`、`开不了 / 起不来`）要换成「或」，不能一律当并列。
数学式保留运算符，`已处理 / 总数` 写成 `已处理 ÷ 总数`。

例外是代码与路径里的斜杠，保持原样。标签路径 `旅行/夜景` 是标识符的一部分，
改了就查不到标签。

三、**全角标点，半角只用于代码**。中文括注用 `（）` 不用 `()`，
注释里的引语统一用 `「」`，不要出现 `“”` 与 `"…"`。句末该有标点就有，别让句子悬着。
C# 字符串字面量里的 `"` 属于代码，不在改动范围内。

**块末一律带句号，续行不带。** 一个注释块的最后一行写完一个完整意思就收句号，
中间折行的续行不加标点。句号只在结尾是汉字、`</c>`、`</see>` 时补上，
已经以 `。`、`？`、`！` 结尾的不重复。

四、**冒号只在行尾用**，用来引出下一行。句中不用冒号。

句中冒号无论后面接的是论断、列举还是定义，都能换成别的说法：

| 句中的写法 | 改成 |
| --- | --- |
| `…是最无歧义的分隔符：它出现时只认它` | 句号：`…是最无歧义的分隔符。出现时只认它` |
| `缩略图：先查缓存，再解码` | `缩略图先查缓存，未命中再解码` |
| `过滤：字段、标签、全文` | `过滤分三层，分别是字段、标签与全文` |
| `占位色：未解码的瓦片` | `未解码的瓦片使用占位色` |
| `设置页：外观、浏览、AI、数据` | `设置页由外观、浏览、AI 与数据四组组成` |

判据只有一句，**这句话能不能不靠冒号说完？** 能，就别用。中文里冒号承担的
「断言 + 论证」关系，句号、逗号、`即`、`含`、`分别是` 都能承担，而且更清楚。

例外只有三个。行尾引出下一行、代码串里的 `：`、异常消息与日志文案里的 `：`。
`无法打开数据库：{path}。` 分隔的是现象与对象，换成分号反而读不清。

## 用词

**术语只用一个词。** 图库统一用 `图库`，不用「照片库」「素材库」「相册」；
画面内容一律叫 `图片`，数据层的 `assets` 一行叫 `资产`，两者不混。
界面上是「图片」，注释在讲 SQL 与仓储时用「资产」，讲画面时用「图片」。
注释里出现「照片」「图像」「素材」时，一律改为 `图片`。

**「文件夹」与「数据目录」分开。** 用户导入的那一层叫文件夹，
`CLIPNEST_HOME` 指向的存储位置叫数据目录，构建输出与缓存路径仍用目录。
混用会让「删除文件夹」这样的句子变得危险。

**「须」会通货膨胀。** 改口语时容易把「要」「得」「应该」一律换成「须」，
结果单字「须」泛滥，多数本该是直陈句。约束分两档：

- 真正的不变量、顺序依赖、越界会坏 → `必须` 或 `不得`
- 一般行为、正常路径 → 直陈句，不加情态词

> ✗ 标注队列须逐张识别，暂停后须立刻停下
> ✓ 标注队列逐张识别；暂停后不再领取新任务，正在处理的一张会完成。

## 改动时怎么做

改代码 → **把注释重写成新事实**，不要追加一段「这次改了什么」。

注释里冒出「现在」「原来」「改成」这三个词，就是信号。把时间轴删掉，只留结论。
改动理由写 commit message，那里可以长、可以带上下文、可以留过程。本仓库的提交用
`feat(app):` 这样的前缀，理由放在正文里，不要塞回注释。

纯注释清理单独一次提交，不夹在功能改动里，评审时只看措辞与事实是否对得上。

注释掉的代码直接删除，Git 里有历史。注释也不署名、不写日期与 PR 号，
`git log` 比注释可靠。

迁移脚本与兼容代码是例外。它们处理的对象就是旧数据，历史是契约的一部分。
`Migration009` 必须写明旧尺寸是怎么记错的，否则下一个人无法判断这条 SQL 是否还该保留。

## 检查

```bash
dotnet build ClipNest.sln     # 编译，注释不参与
dotnet test ClipNest.sln      # 行为回归，与注释无关
```

注释没有编译器兜底。本项目不生成 XML 文档文件，`<see cref="Name"/>` 断链也不会报。
机械项只能在编辑器里全局搜索。下面四类已在首轮清理中清到 0，新改动按此自查：

- `——`：只留真正的插入语
- 中文两侧带空格的 `/`：并列改 `、` 或 `与`
- `**` 与反引号：C# 注释不渲染 markdown
- 句中 `：`：改成句号、逗号或 `分别是`

清理顺序是先机械项、后语义项。机械项可以批量替换，语义项必须逐块读。
两者混在一次提交里，review 会漏掉被替换坏的条件句。

**改动叙事这一条搜不出来。** 词表法（`现在…`、`原本…`、`换成…`）也不可靠，
命中的多数是行为描述，例如「排序换成按拍摄时间」「悬停时换成勾选」，不是历史。
判据只能由人来读。注释里的时间词是给读者的，还是给「记得旧版本的人」的？后者才该删。

所以这条规矩只能靠习惯，不能靠 CI。
