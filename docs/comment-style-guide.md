# 注释规范

本规范适用于 `src/`、`tests/` 下的 C# 与 XAML（`.axaml`）源码，以及仓库根目录的 `.csproj` 与 `.props` 文件。自动生成代码、`obj/` 目录与第三方源码不在范围内。

异常消息、日志、断言消息与界面文案同样遵循本文的语体、用词与标点要求。

## 写什么，不写什么

### 应该写的四类内容

1. **约束**：说明为什么必须按当前方式实现，包括前置条件、执行顺序与调用时机。
   > 缩略图先写入 `.tmp` 临时文件再重命名，确保读取方要么看不到文件，要么读取到完整文件。

2. **失败模式**：说明违背当前做法会引发什么问题，避免后续改动重复引入同类故障。
   > 解码、编码与落盘不能回到 UI 线程的同步上下文，否则首次浏览时每张图片都会阻塞主线程。

3. **契约**：说明调用边界与状态语义，例如调用方职责、调用时机及并发行为。
   > 暂停后不再领取新任务；正在处理的一张会继续完成，恢复时由调用方唤醒。

4. **不变量**：说明此处恒成立、可供其他模块依赖的事实。
   > 节点之间至少保留一张缩略图的间距，放大后可以直接逐张点选。

### 避免写的四类内容

1. **改动历史**：不写「原来是 X，现在改成 Y」「第一版」「后来换掉了」等演变过程。注释只描述当前事实，改动背景应写在 Commit Message 中。
   - ✗ 现在缩略图按固定档位缓存。
   - ✓ 缓存按长边分档；每档都在磁盘与内存中各留一份，因此只取固定档位，缩放条每移动一格不会生成新文件。

   **例外**：数据库迁移脚本与兼容代码处理的对象本身就是旧数据，历史成因属于契约的一部分。例如 `Migration009` 中说明「早期按 EXIF 原始像素记录尺寸」，是判断该 SQL 作用的必要依据。

2. **调试过程痕迹**：不留「实测」「截图里」「调试时发现」等排查现场记录。有价值的结论和数据可以保留，但应改写为客观陈述。
   - ✗ 实测这台机器上 GPU 比 CPU 快三倍。
   - ✓ DirectML 覆盖 Windows 平台的 AMD、NVIDIA 与 Intel 显卡，初始化失败时回退至 CPU。

3. **以测试为由解释设计**：不写「为了单测」「否则测试过不了」「便于测试」。设计理由应从模块职责与扩展性出发说明，而非从测试困难出发。
   - ✗ 抽成接口是为了单测能替换解码器。
   - ✓ 解码器按文件扩展名选择，新增格式时无需修改调用方。

4. **复述代码实现**：代码本身已经清晰表达的逻辑，注释不再重复。常见冗余形式包括以下三类：
   - **逐行复述步骤**：执行步骤已在代码中体现，注释应说明顺序约束或容错机制。
     - ✗ 建库时依次执行各版本迁移。
     - ✓ 每个迁移单独提交并立即写入 `user_version`；中途崩溃后下次启动会从断点继续，已完成的迁移不会重放。
   - **直译标识符**：不要将方法名直接翻译成中文作为摘要，例如在 `GetOrCreateAsync` 上写「获取或创建缩略图」。摘要应交代输入条件、缓存行为或失败返回值等契约。
     - ✗ 获取或创建缩略图。
     - ✓ 缓存命中时直接返回路径；未命中时解码并写入缓存，解码失败返回 `null`。
   - **无信息量的局部变量注释**：仅说明变量存储了什么（如「已扫描文件的集合」）应当删除。若注释说明了关键的性能或算法收益，例如「`known` 字典将单文件查找从线性扫描降为常数时间」，则可以保留。

### 快速自检

撰写或审阅注释时，可用以下两个问题判断取舍：

- **删掉是否有损**：如果删掉这条注释，后续维护者是否会遗漏关键约束或引入隐蔽问题？如果不会，则不必写。
- **新人能否看懂**：不了解历史版本的读者读完后，是否能直接明白「这里为什么这样实现」？

## 语体与用词

### 书面、客观的技术表述

注释属于技术文档，应像规格说明一样准确、克制，避免口头讲解式的随意表述。口语和比喻虽然直观，但往往模糊了行为边界。具体遵循以下四条：

1. **不拟人**：模块、解码器、队列、线程等技术对象不使用「想」「挡」「吐」「自己」等拟人表达。
   - ✗ 解码器自己会挡掉坏文件。
   - ✓ 解码器在文件头无法解析时返回空值。

2. **不用口语副词与填充词**：避免「一把」「干脆」「才真的」「就是」「其实」「差不多」等口头词。
   - ✗ 导入时干脆把整批写进一个事务。
   - ✓ 整批写入单个事务，中途失败时不会残留部分资产。

3. **数据流使用准确动词**：避免「灌」「塞」「喂」「吐」等非正式动词，改用「写入」「推送」「提供」「产出」等术语。
   - ✗ 导入完成后把整个图库灌给标注队列。
   - ✓ 导入完成后向标注队列发送一次信号，由队列从数据库领取待标注资产。

4. **使用完整条件句**：将松散的口语短句与破折号插叙改写为「主语 + 条件 + 结论」的完整句式。
   - ✗ 看不懂的就不猜，交给调用方保留原样。
   - ✓ 证据不足时不作判定，由调用方保留原值。

常见口语替换参考：

| 避免使用 | 建议改写 |
| --- | --- |
| 挡一道 | 预先拦截 |
| 刷屏 | 日志洪泛 |
| 踩到 | 落于、触及 |
| 来回撞 | 反复重试 |
| 看不出 | 无法判定 |
| 就得 | 必须 |
| 别再 | 不得 |
| 收工 | 结束 |
| 顶在（UI 线程上） | 占用（UI 线程） |
| 引擎自己、线程自己 | 引擎自身、线程本身 |

有两类情况不属于口语，无需强行改写：

- **领域术语**：项目内约定俗成的专业词应保留，例如 UI 交互中的「拖拽」、数据表中指代 `asset_files.is_primary` 记录的「主文件」、虚拟化画布中的「瓦片」。将这些词改为泛化表达反而会降低精度。
- **自然书面语**：本身属于规范书面汉语的说法不必刻意改得生硬。例如「宁可先留空位，也不让瓦片重叠」清晰自然，不必强改为「优先留空位而非重叠」。

### 术语与情态词统一

- **图库、图片与资产**：整个图库统一称为「图库」，不使用「照片库」「素材库」「相册」。面向画面内容和界面展示时统一称为「图片」，不使用「照片」「图像」「素材」；涉及数据库 `assets` 表与仓储层记录时统一称为「资产」，按层级区分、不混用。
- **文件夹、数据目录与目录**：用户导入的层级称为「文件夹」；`CLIPNEST_HOME` 指向的持久化根目录称为「数据目录」；构建输出与缓存等内部路径称为「目录」。三者严格区分，避免类似「删除文件夹」的表述产生歧义。
- **克制使用情态词**：改写口语时不要将「要」「得」「应该」一律替换成「须」，以免生硬。硬性约束（涉及不变量、顺序依赖或越界故障）使用「必须」或「不得」，常规行为或默认路径直接使用直陈句，不加多余情态词。
  - ✗ 标注队列须逐张识别，暂停后须立刻停下。
  - ✓ 标注队列逐张识别；暂停后不再领取新任务，正在处理的一张会继续完成。

## 标点与括号

### 全角标点与句末句号

- 中文注释统一使用全角标点，半角标点仅用于代码片段。中文括注使用 `（）`，引语统一使用 `「」`，不使用 `“”` 或半角 `"`；C# 字符串字面量本身的引号除外。
- 注释块在语义完整处以句号收尾，结尾为汉字、`</c>` 或 `</see>` 等内联标签时补全句号，已以 `。`、`？`、`！` 结尾则不重复。多行注释因行宽折行时，中间续行不加句号。

### 破折号

不将破折号用作普通分句连接词，应根据前后逻辑替换为对应标点。由于句中不使用冒号，也不改为句中冒号：

| 句间关系 | 改写方式 |
| --- | --- |
| 分句延续（补充谓语或同位说明） | `，` |
| 因果、推论 | `，因为……` / `；否则……` / `。` |
| 并列、递进 | `。` |
| 转折 | `；但……` / `。` |

- ✗ 创建会话。`allowGpu` 为假时固定走 CPU —— CLIP 的输入是动态形状，放 GPU 上会反复重编译
- ✓ 创建会话。`allowGpu` 为假时固定走 CPU；CLIP 的输入是动态形状，放 GPU 上会反复重编译。

破折号仅在极少数需要插入独立补充语、且用逗号会导致层次不清时保留。改写后建议通读确认，前后可独立成句时用句号，后半句依附前半句时用逗号或分号，难以取舍时优先用句号。

### 句中冒号

冒号仅用于行尾以引出下一行内容，不在句子中间使用。句中常见的定义、列举与因果关系，均可改写为更直接的句式：

| 句中冒号写法 | 建议改写 |
| --- | --- |
| `……是最无歧义的分隔符：它出现时只认它` | `……是最无歧义的分隔符。出现时只认它。` |
| `缩略图：先查缓存，再解码` | `缩略图先查缓存，未命中再解码。` |
| `过滤：字段、标签、全文` | `过滤分为字段、标签与全文三层。` |
| `占位色：未解码的瓦片` | `未解码的瓦片使用占位色。` |
| `设置页：外观、浏览、AI、数据` | `设置页包含外观、浏览、AI 与数据四组。` |

**例外**：行尾引出下文、代码片段内部的冒号，以及异常消息和日志中分隔现象与对象的冒号（如 `无法打开数据库：{path}。`）。

### 斜杠

- 中文并列不使用 `/`（例如不写 `亮边 / 暗边`）。两项并列用 `与`，三项及以上用 `、`；原本表示选择关系的（如 `打开 / 关闭`）改用 `或`，不混用。
- 代码、文件路径与标签路径（如 `旅行/夜景`）中的斜杠属于标识符或路径语法，保持原样。纯中文说明中若需表达除法运算，可使用 `÷`（如 `已处理 ÷ 总数`）以避免与并列斜杠混淆。

### 括号

能直接融入句子的信息应写成正常句子成分，避免频繁插括号打断阅读。同一句内不出现两对及以上括号，否则应拆句或重写。

允许保留的三类场景：

1. **枚举与举例**：`格式角标（jpg、png、heic）的底色`
2. **数值、单位与区间**：`缩略图长边（1024 px）`、`年份区间（2020..2024）`
3. **标准与出处**：`对比度 ≥ 4.5:1（WCAG AA）`

其余情况应改为正文句式：

- **补充说明** → 改为分句
  - ✗ 导入完成后刷新图库（只刷新一次）。
  - ✓ 导入完成后刷新图库；每次导入只刷新一次。
- **同义解释** → 改为「，即……」
  - ✗ 列表主标题（文件名）。
  - ✓ 列表主标题，即文件名。
- **跨引用** → 改为「，见……」
  - ✗ 选中态会额外加粗（见 `ThumbnailGridCanvas`）。
  - ✓ 选中态额外加粗，见 `ThumbnailGridCanvas`。
- **返回值元组** → 直接陈述
  - ✗ 编译搜索结果 →（SQL, 参数）。
  - ✓ 编译查询，返回 SQL 与绑定参数。

## 注释形式与 XML 文档

### 篇幅与行宽

- 单个普通注释块不超过 3 行；若超出，应先确认是否在复述代码结构而非说明约束。`<remarks>` 单独计算，记录推导过程时最多 6 行，更长的内容应移至 `docs/` 文档。
- 单行不超过 80 字，建议控制在 50 字左右，避免中文长行阅读时串行。需要完整复制的命令行（如 `dotnet test ...`）不强行折行。
- 行数限制与行宽限制冲突时，优先保证行宽，宁可多折一行也不写超长单行。

### 注释类型与位置

- `///` 用于声明类型与成员的契约及设计理由；`//` 仅用于说明单行代码非直观的意图。
- 文件级说明挂在命名空间下的第一个类型上，不写 `// File: xxx.cs` 这类无信息量的文件头。
- `.axaml`、`.csproj` 与 `.props` 中的 `<!-- -->` 遵循与 `///` 相同的写作要求，重在说明约束而非操作步骤（可参考 `Directory.Build.props` 中固定 `x64` 平台的注释）。

### 不使用排版语法

- 注释采用纯文本散文形式，不使用 Markdown 列表、标题、表格、`**` 加粗或反引号。C# XML 文档注释不会渲染 Markdown，这些符号会原样出现在 IDE 悬停提示中。
- 不使用 `<b>`、`<i>` 等样式标签；需要强调时通过调整语序或独立成句表达。

### C# XML 文档标签约定

- `<summary>` 是 IDE 悬停提示的主要展示内容，`<remarks>` 通常默认折叠。首句应能独立说明「用途与适用条件」，推导细节与失败模式放入 `<remarks>`。
- 引用类型或成员使用 `<see cref="Name"/>`，引用参数使用 `<paramref name="x"/>`，行内代码使用 `<c>...</c>`，不使用反引号。本文为便于 Markdown 阅读使用反引号标记代码，写入 `.cs` 时请转换为对应的 XML 标签。
- `<param>` 只补充参数名无法体现的约束，例如单位、范围、估算规则或所有权，不写「要处理的图片」等冗余描述。可参考 `ThumbnailSizing.ForBox` 的写法：
  ```xml
  <param name="sourceRatio">图片宽高比；未知时按显示框较长的一边估算。</param>
  ```
- `<returns>` 说明空值、边界条件与失败语义，不写「返回结果」。
- `<exception>` 说明触发条件，不写「可能抛出异常」。
- 实现接口成员时使用 `<inheritdoc/>`，不在实现类中重复复制接口契约。

## 异常消息、日志、断言与界面文案

- **异常消息与日志**：使用书面语，并同时说明「发生了什么」与「下一步如何处理」，避免只给出笼统报错。
  > `无法打开数据库：{path}。请确认目录可写，或设置 CLIPNEST_HOME 指向可写目录。`
- **断言消息**：采用「预期现象 + 原因」的完整句式，便于测试失败时直接定位意图，避免用破折号草率连接。
  - ✗ `"分类数应该等于根标签数 —— 未分类也单独成簇"`
  - ✓ `"分类数应该等于根标签数，因为未分类也单独成簇"`
- **界面文案**：面向用户的提示应写成自然、完整的句子。修改文案时务必保证插值占位符与 XAML 绑定完整对应，例如 `$"语义索引 {stats.Ready}/{total}"` 中的 `{stats.Ready}`、`{total}`，以及 XAML 中的 `{DynamicResource Brush.Text.Primary}`，不得改动绑定名或增删占位符。

## 维护与自查

### 修改与清理原则

- **同步更新**：修改逻辑时直接将注释重写为新事实，不追加变动说明；改动背景写在 Commit Message 正文中（本仓库遵循 `feat(app):` 等约定式提交格式）。
- **核对归属**：移动、拆分或重构函数时，同步迁移对应注释，防止注释滞留在旧位置导致语义错位，例如将 `ThumbnailSizing` 的换算说明误留在调用控件上。
- **清理冗余**：废弃代码直接删除，不以注释保留；注释中不写署名、日期或 PR 编号，历史追踪统一依赖 Git 记录。
- **拆分提交**：纯注释整理建议单独提交，不与功能改动混在一起。批量清理时先处理可检索的格式项，再逐段审阅语义项，避免机械替换破坏原有句意。

### 提交前自查

本项目未开启 XML 文档文件生成，因此 `dotnet build` 与 `dotnet test` 不会检查注释内容或 `<see cref="..."/>` 断链。提交前可通过全局搜索排查以下常见格式项：

- `——`：检查是否误用作普通分句连接词。
- 中文两侧的 `/`：检查是否误用于并列或选择关系。
- `**` 与反引号：检查 C# 注释中是否混入 Markdown 标记。
- 句中全角 `：`：检查是否可改写为普通句式，行尾引导、代码片段以及异常与日志文案除外。

「现在」「原来」「改成」等时间词无法仅靠关键词可靠排查，因为部分命中属于正常的运行时行为描述，例如「排序切换为按拍摄时间」「悬停时切换为勾选态」。这类内容需人工通读判断，只要时间词是在对照旧版本而非描述当前状态切换，就应当删除。
